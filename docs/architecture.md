# Architecture

rpg-engine is a set of commands over a campaign folder of markdown and YAML files, served as a command line (`rpg`) and as an MCP server (`rpg mcp`), with a dashboard for the player. This is how its parts work together; [structure.md](structure.md) says where they are and what each depends on, the code says the rest. [AGENTS.md](../AGENTS.md) holds the development rules.

Comments and tests cite rule codes such as `INH-4` or `CON-1`: `grep -r "INH-4" src test` finds the code and the tests of a rule.

## 1. A command

A command is defined once with `defineCommand` ([core/registry.ts](../src/core/registry.ts)): `name`, a `description` written for an AI, a zod `input`, flags (`readOnly`, `alwaysLoad`, `needsPlayer`, `slow`, `positionals`), `run(input, context)` and `format(result)`. [commands/index.ts](../src/commands/index.ts) lists them; the CLI ([cli/command-line.ts](../src/cli/command-line.ts)) and the MCP server ([server/mcp.ts](../src/server/mcp.ts)) are generated from that list, and the dashboard calls `view` through `/api/view`. The MCP server checks a tool's input itself, showing the host the same strict schema, and answers a wrong call with all the tool's parameters. Where a description names a game's thing it writes a placeholder, such as `{{counter}}` ([core/examples.ts](../src/core/examples.ts)): the MCP server fills it with the names of the campaign's system ([commands/shared/examples.ts](../src/commands/shared/examples.ts)) and again after a call that changes the system; the CLI and the reference use neutral names.

- **Context** ([core/context.ts](../src/core/context.ts)): everything from outside, injected: the folder, randomness, time, ids, the system folders; on MCP also the player's forms, the dashboard, the session store. Tests use `testContext()` from [test/support.ts](../test/support.ts).
- **Store** ([core/store.ts](../src/core/store.ts)): each call reads a file once, keeps what it parsed deep-frozen, and writes through it. The MCP server keeps a `SessionStore` ([core/session-store.ts](../src/core/session-store.ts)) across calls, watching the campaign's folders; what changed outside the session is told to the master at the next call ([commands/shared/campaign/outside.ts](../src/commands/shared/campaign/outside.ts)).
- **Log**: a command that changes the game appends lines to `log.jsonl` ([core/log.ts](../src/core/log.ts)), each `public` or `hidden`.
- **Chats**: the MCP server copies the campaign's chats that Claude Code and Codex keep in their own folders into `sessions/`, as it starts and then every few minutes, a markdown file each with the player's and the master's words and when, without tools or reasoning ([chats/](../src/chats/), [server/chats.ts](../src/server/chats.ts)). Saves leave them out. A load undoes the stretch from when its save was made to when it was loaded: the log's `save-loaded` lines, which go back with the saves, give those stretches, the copies mark them, and the `chats` command, which finds and reads the past chats, leaves them out ([commands/shared/campaign/chats.ts](../src/commands/shared/campaign/chats.ts)).
- **Book**: the master writes a chapter of prose with `book` where the story turns, telling the closed scenes since the last chapter: a markdown file in `book/` that names the log lines that opened its scenes; a chapter whose scenes a load undid is left out, with those after it, until written again. `scene close` names the scenes waiting for it, and `status` too once they are many, and the first call in a chat says how to write it; the Journal's view gives the chapters, which the dashboard sets as a book and downloads as Markdown or a web page ([commands/shared/campaign/book.ts](../src/commands/shared/campaign/book.ts), [dashboard/journal/book.tsx](../src/dashboard/journal/book.tsx)).
- **Output**: an AI reads it. Errors say what went wrong and what to call next; a refused write says "Nothing changed". Everything is checked before the first write.

## 2. Data on disk

### A campaign

```
campaign.yaml   settings
state.yaml      the present: mode, date, open scene, journey, the master's mood
log.jsonl       one JSON line per change
world/          the pages: characters/ places/ factions/ quests/ items/ events/ topics/ creatures/
rules/          house rules (optional)
images/         pictures (optional)
.saves/         saves, one zip each
.imports/       documents being made adventures, each with its pieces, notes and adventure
exports/        adventures exported from the campaign, kept out of the saves
sessions/       the chats as text, copied from the AI hosts, kept out of the saves
sessions/table-chats/   the chats of the table with the master, a file of JSON lines each, one message a line, kept out of the saves
book/           the story told as a book, chapters of the master's prose, each telling a few closed scenes, kept out of the saves
.player/        the player's notes
AGENTS.md, CLAUDE.md, .mcp.json, .claude/, .codex/, .agents/, opencode.json, .opencode/   tell AI hosts where rpg-engine is, memory off, the doorbell
```

`init` creates it ([campaign/create-campaign.ts](../src/campaign/create-campaign.ts), host files in [campaign/host-files.ts](../src/campaign/host-files.ts)); given a campaign's folder, it only brings the host files up to date, as the MCP server does as it starts. Both also add the rpg server to Antigravity's own servers, `~/.gemini/config/mcp_config.json`, when Antigravity is installed: its app starts one server for every folder, in its own, with no campaign. Started outside a campaign, `rpg mcp` is a router ([server/route/](../src/server/route/)): it keeps a child `rpg mcp` in its own folder, and one for each campaign a call plays, started the first time with the client's handshake again, whose answer stays with the router. A `tools/call` whose conversation (`_meta["antigravity.google/conversation_id"]`) is noted as playing a campaign goes to that campaign's child; any other call, and every other request, to its own folder's, never to another campaign's. A child's own requests to the client get ids the router makes unique, and the answers go back to it; the client hears `notifications/tools/list_changed` when a call goes to a child whose tools it did not list; a child that ends has its calls answered with an error and starts again at the next; every child ends with the client. A conversation with no note that calls in the router's own folder is told to have the player open the campaign's folder and start a new chat there, and `init` there needs a full path. `rpg --approve` notes the conversation, one file per conversation in the engine's data folder (`antigravity-conversations/`), from the campaign of the hook's folder; notes not written for 30 days go as the router starts. Its lines on stderr begin `rpg mcp router:`, one for each call with the folder of the child it went to. In a run of the engine's helper (`RPG_HELPER`), `rpg mcp` leaves at once without a word, so that the helper's host keeps its tools as they were. A campaign is the nearest folder upwards with a `campaign.yaml`.

### Pages

A page is a markdown file under `world/` ([pages/world.ts](../src/pages/world.ts)): its name is the file name, its type the first folder, its fields the YAML frontmatter. The format is Obsidian's: `[[links]]`, headings make sections, `> [!secret] Name` blocks. Standard fields ([pages/standard-fields.ts](../src/pages/standard-fields.ts)) have fixed meanings; the others are free or declared by the system. Commands write a page with `writePage` ([pages/write-page.ts](../src/pages/write-page.ts)).

### An adventure

A folder or a `.zip` with `adventure.yaml` (title, about, language, version, author, license, needs, levels, content, length, party, start, opening) and only `world/`, `images/` and `rules/`, as a campaign has them, and its layers over the pages of the game system it needs, in `layers/<system>/world/` ([adventures/](../src/adventures/)). `package install` copies it into the campaign whole or not at all: pages under `world/<type>/<Adventure>/`, the rest under a folder of its own, the dates of the frontmatter moved to today; the log says which adventures are installed, so they go back with a save. `package export` writes the world as it was at the start, without the player characters ([commands/shared/books/adventures.ts](../src/commands/shared/books/adventures.ts)). A layer goes to its page's own path, where it is the campaign's from then on: the campaign's own layer over the same page stays and the adventure's is left out, by name; taking the adventure out takes each layer still as it wrote it, by the print the log keeps; an export carries the campaign's layers as they are now, and says in the system's credits that its material is changed ([commands/shared/books/adventure-layers.ts](../src/commands/shared/books/adventure-layers.ts)). A document without `adventure.yaml` is made an adventure with `import`: the engine reads its text and pictures, a PDF's pages without readable text by Windows' OCR ([documents/](../src/documents/)), keeps it in pieces in `.imports/<title>/` with the mark of how far it is ([importer/](../src/importer/)), and a helper outside the chat, the player's Claude Code or Codex, or in OpenCode's chat OpenCode first with the player's own model and an agent fenced to the folder, given in `OPENCODE_CONFIG_CONTENT` and its session deleted after, or in Antigravity's chat its `agy` first, from an empty folder of its own, fenced to the import's folder by its settings and by the hook `rpg --fence`, reads it piece after piece, proposes starting points, then sets the world at the one chosen ([commands/import/run.ts](../src/commands/import/run.ts)); the result is an adventure folder for `package install`, and the document's text leaves `.imports/`. The dashboard tells how far an import is, from the document being opened (`.imports/opening.yaml`, with the pages the OCR has read) to the world written, and reads it again every few seconds while it works by itself. Where no helper is installed, the master reads the pieces in the chat and writes the pages into the world. The Packages page lists them, adds one from a `.zip` and exports the campaign ([dashboard/packages/packages.tsx](../src/dashboard/packages/packages.tsx)).

### A game system

A game system is a folder that holds `system.yaml`, `world/` (pages, as in a campaign), `rules/` (chapters of rules text), `images/`, `LICENSE.md`, `versions/<name>/` (a version of its rules in the same shape, read over the rest as the campaign's `ruleset` says). The engine brings `systems/free/` alone; any other is a package npm installs into the player's data folder, with `package install`, and lives in a repository of its own with its tests. The MCP server installs one of ours that a campaign plays and this computer lacks as it starts, once the world is read; its first call waits for it, before the dashboard opens, and says so in its answer ([commands/package/install.ts](../src/commands/package/install.ts), `installCampaignSystem`). [systems/read.ts](../src/systems/read.ts) validates it into a frozen `GameSystem`. A system may bring code, `package.json` and `src/` built to `dist/`: [systems/code.ts](../src/systems/code.ts) loads it as an entry starts, into the `Context`, and [commands/shared/packages/hooks.ts](../src/commands/shared/packages/hooks.ts) calls its hooks, and the extensions', after the commands' writes. See [game-systems.md](game-systems.md).

### A package's code

An extension's code and a game system's have one contract, [core/packages/api.ts](../src/core/packages/api.ts), exported by [index.ts](../src/index.ts): `PackageEntry` gives `PackageCode`, with its commands, what it does as time passes, its widgets' hooks, and the hooks after the engine's writes, called at once, the system's first ([commands/shared/packages/hooks.ts](../src/commands/shared/packages/hooks.ts)); the kind decides only the role, one system for a campaign with its data in `system.yaml`. The game it reaches is `Game`, read by widgets as `GameView`. [core/packages/declarations.ts](../src/core/packages/declarations.ts) holds what both declare alike: the API number, read from `rpg-engine.api` in `package.json`, and the icons, widgets and figures of `extension.yaml` and `system.yaml`; the pages a card stands in and the room of a figure are the contract's, which [page.ts](../src/page.ts) passes on to the page code. [commands/shared/packages/code.ts](../src/commands/shared/packages/code.ts) gives the campaign's packages, the system first, their commands and their game. The contract and the schema of both files are the API, whose number goes up with every addition a package may use, a new key too; the engine reads a range of them.

### The dashboard

The MCP server opens it on 127.0.0.1 as the chat starts, without opening the browser, at the campaign's own port: worked out once from its folder, then kept in the campaign's `.dashboard-port`, which git leaves out as this computer's, and changed only when another program or campaign holds it ([server/dashboard/ports.ts](../src/server/dashboard/ports.ts)). Another chat of the campaign gives the link of the page the first one serves, which rings the doorbell for that chat alone, and serves it at the same port once that chat closes. The server ([server/dashboard/index.ts](../src/server/dashboard/index.ts)) answers `/api/view` and the player's few actions (answers, notes, settings, saves, packages of ours, a layer of the campaign taken off a page of the system with `/api/layer`, and what their character does, a sentence the master hears at the head of their next call: [server/player-acts.ts](../src/server/player-acts.ts), rung in by the doorbell, `rpg --listen`, the Stop hook of Claude Code and Antigravity, run in OpenCode by the campaign's plugin, which asks `/api/bell?words` and is given the sentences themselves, with their ids, which it sends back as it takes them (`/api/bell?took=`): held until a call of the master begins, and given back to those waiting when that call begins before the hook took them, or none begins within a minute ([server/bell/](../src/server/bell/), [plugins/opencode.js](../plugins/opencode.js)), or queued in Codex's thread), sends `/events` when files change (no data: the page reads `view` again), gives the extensions' widgets as their hooks show them (`/api/widgets`), and serves pictures by name only. The Packages page reads the engine itself at `/api/engine`: a GET gives `{version, installed?, latest?, update?, failed?, install, folder?, working?}`, `version` being the one this server runs, read as it started, `installed` the one npm put on disk since, which a new chat runs, `update` whether npm's latest is newer than that, and `install` being `global` (npm's global folder, which it updates), `link` (an `npm link` of `folder`, for development) or `other` (`folder`, any other way), `failed` why npm could not be asked; npm's latest is asked at most once a day, kept in the player's folder (`engine-update.json`), and when npm did not answer asked again after an hour ([server/dashboard/engine.ts](../src/server/dashboard/engine.ts)); the page reads it once as it opens, for its notice of a newer engine. A POST `{action: "update"}`, from the page alone, asks npm anew, then the player's yes in a window of their computer (a no holds for the session, `declined`; no window, `no-window`, with the terminal's command), installs npm's latest globally with npm and answers 202 `{kind: "engine-updated", version, restart}`, `restart` being `chat` (a new chat takes the new engine) or `app` (the app opened again), else 400 `{error}` with what to do, and 409 while another package's work goes on; where nothing updates it, as in the demo, a GET gives `{version}` alone. Until then the chat, its server and the page go on with the engine they started with. A catalog entry whose latest needs a newer engine has `newer: {version, engine?}`, the version offered being the newest this engine reads. The page ([dashboard/app.tsx](../src/dashboard/app.tsx)) writes its words with `t()` from [dashboard/i18n/](../src/dashboard/i18n/), and a refusal of the packages, the library or the engine's update by the `code` and `values` the server sends beside the engine's words ([core/refusal.ts](../src/core/refusal.ts), [dashboard/parts/refusals.ts](../src/dashboard/parts/refusals.ts)); Help's guide is [dashboard/guide/](../src/dashboard/guide/). It knows no game: a game's cards and panels, as the 5e's death saves and hit dice, are its packages' widgets and page modules, mounted where the page keeps a place ([dashboard/packages/page-code.tsx](../src/dashboard/packages/page-code.tsx), [dashboard/sheet/person-panel.tsx](../src/dashboard/sheet/person-panel.tsx), [dashboard/packages/ask-card.tsx](../src/dashboard/packages/ask-card.tsx)); a rest's dice with no card are the question's own buttons ([dashboard/play/asked-dice.tsx](../src/dashboard/play/asked-dice.tsx)).

`rpg table`, the campaign's table ([server/table/](../src/server/table/)), serves the page with no chat open and writes where it is found in the player's data folder (`tables/`, readable by the player alone): its local socket, a named pipe on Windows, and a token new at each start. `rpg mcp` in the campaign then knocks with that token and its engine's version, and once the table lets it sit, one chat at a time, it only passes its host's lines to a server the table makes for that chat, over the table's own files and page, with the few names of its environment that say its host's session. Another server of the same chat, as the one a character's subagent starts for itself in Codex, sits beside it on the same files and page, and only looks, with `view` as a character: it leaves without the chat, and goes when the chat's own server goes. One refused because another chat sits serves only looking too, saying why, so that one engine writes the campaign; anywhere else, refused for another reason, stale or slow, it serves as before. If the table goes while a call waits, the pipe answers that call with an error and ends. The table ends by itself after five minutes with no chat and no page, and once the code of a package it loaded is no longer the code on disk and no call runs; the master is told to start it again. `rpg table --stop` in the campaign asks it to end with its place's token, and waits until it did, its place and its process gone, saying so, or that there was none, that it does not answer, or that it is still ending after a minute; it never stops it from outside. However it ends, a turn of its own chat is stopped as the player's Stop does, the chat let go as below, and its process waits, at most 35 seconds, for the AI apps it started to end by themselves, as on Windows its exit would stop them at once; so does the launcher, and either after an error nobody caught, once its chat is let go; the log says, with the time, that they ended, or how many the exit stops and which. A second `rpg table` asks the first whether it is there before it takes its place. The table can also keep a chat of its own with the master, opened from the page in the host's own program, which the page then speaks to: while it is open only its servers sit, the player's sentences on the page go to it one a turn, and the choice of host, model and effort is kept beside the table's place for the next chat to take up: the model as the player chose it, the name the host gives the model it runs shown apart. Every message of the chat is kept in the campaign, in `sessions/table-chats/`, a file for each chat named by when it was opened (`2026-11-25 21-04-17.jsonl`), one message a line as JSON once it is complete: the master's words of a turn at its end, or when a question or a roll comes between them, or as the chat closes; a question as it begins and again as it ends; a line where each turn of the master's ended. Each line is appended whole, so that a table cut short at any point leaves at most a last line that does not read. A chat taken up again continues its file, on a new line after a torn one, and shows its last 200 messages; one opened anew starts a new file; a line that does not read is left out. Read back, no question waits: one still waiting was left as its table ended, and is written so at the next write; the chat taken up says it was cut short (`cutShort` on `/api/master`'s `chat`, until the next turn begins) where such a question ends it, or where the player's last words have no end of a turn after them. As a table's first page listens, the table takes up by itself the campaign's last chat, where the host said its session and the player did not close it, with the same host, model and effort, and sends the host nothing; a chat the player closed waits for the player to open one. The page lists every host the engine knows, with whether the table can open it and whether its program is on this computer, and the models each found host offers: asked of its program in the background the first time it is shown, kept ten minutes: by its protocol's first request and nothing more, or, for a host of the Agent Client Protocol, by a new session in the campaign's folder, deleted after where the host can; the efforts allowed are the chosen model's own, and a model the host did not list is still taken. The launcher offers the same for a new campaign's first chat. Each host comes with its account and how it is signed in and installed, as on the launcher (below), and the page asks the same of `/api/master` (`{ signIn }`, `{ install }`, `{ hosts: true }`); a host the player is known to be signed out of is never started: the chat is refused with `code: "signin"` beside the words, and one that finds it so, or loses it, ends with the same code and no word that sends the player to a terminal. A model may be the host's own default (`advised`), and in OpenCode it names its provider (`group`) and whether it is paid apart on the player's key (`metered`), which the engine never proposes by itself where another is listed: OpenCode's own models come first, then those run on this computer, before its list is cut. An account signed in with an API key is `metered` too. Between two turns `{ model: { model, effort? } }` asks the host for another model, the player's next words held until it confirms it; an effort not given stays where that model takes it; the choice kept follows, and the chat says it in a line of its own, marked for the page (`code`: `model`, or `model-kept` where the host refused it and the chat goes on with the model before). The master gets the rpg commands, the host's search on the web and its reading of a page, its subagent that plays a character, and reading the campaign's folder alone, each permission given for that call alone; a tool of another kind, or a read outside the folder, that a host runs without asking stops the turn, which fails naming it; a chat whose model the host does not confirm ends. A subagent's words are never the master's, nor its tools: what it runs is held to the same limits, and a subagent other than the character's stops the turn (Codex says which agent a thread is only when asked, with `thread/read`); Claude Code, which starts a subagent without asking, is made to ask, and one other than the character's is refused before it starts, but its own reader of a page of the web (`web-fetch`), which a Claude Code with no `WebFetch` of the master's own uses, and which counts as reading a page. A turn the host ends with no word after a tool the table refused, as Antigravity does by itself, is followed once in the player's turn by a line of the table's to the master, to go on with the game's commands; only a second such turn tells the page the master wrote nothing. A host that goes on by itself once its turn ended, as OpenCode does to tell a character's answer, opens a turn of its own, held to the same limits, its words a new message and the player's waiting for its end: 20 seconds in which neither the master nor its subagents said anything and no tool of the master's runs; it is never followed, nor said empty. Claude Code is driven by its own protocol, and Codex by its own JSON-RPC (`codex app-server`); OpenCode by the Agent Client Protocol (`opencode acp`, the campaign's folder in `PWD`), where the rpg commands run inside its tool `execute` and are named only as it ends, and where the table answers the permissions the host asks but cannot take away beforehand the tools the campaign's `opencode.json` or the player's global configuration lets run without asking; Antigravity by the same protocol (`agy acp`), with no MCP server passed, as rpg comes from the campaign's `.agents/mcp_config.json` or the player's own, and the model set by `session/set_model`; its tools are read by their names and inputs: rpg's commands through `call_mcp_tool`, the descriptions of those commands and the answers of the chat's own tools that it keeps in its folder, its subagents for a character or a picture. Between the master's words the chat keeps what the engine did: each question the master asks on the page, waiting, then answered with the answer in words or left without one, and each roll the player may see, in a line and as the Rolls card gets it; a hidden roll never. In this chat the master writes `[roll <id>]` where a roll decides, and the page draws the roll there; `ask` refuses a new question while a roll of the player's in the turn that runs has no such mark in the master's words. While a question waits that takes the player's own words, the words said in the chat answer it, as on the question's bar, and the master's turn goes on. The page hears of the chat alone by the event `chat` on `/events`, and reads `/api/master` then. Where the table's environment names a file in `RPG_MASTER_TRACE`, every line between the table and the host's program is added to it, with its way and time, after a first line that warns it may hold the account's name and the whole chat; the host's process never gets that variable. With no page for the same five minutes, the chat's turn is stopped, and out of a turn the chat is closed, its server sent away. A host's program the engine is done with, as one that gave its models or was late to, a chat the player or the table closes or one that cannot play, has its input closed and ten seconds to end by itself, as it may be saving the player's login, before it is stopped. A list of models that failed or came empty is asked again after a minute, and any list once the host's account changed; never the models of the host whose chat is open or opening. A change of model is said in the chat, and followed by the choice kept and what `/api/master` shows, only once the host took it (`changeTaken`); a refused one has only its line `model-kept`, or `model` with `dropped` where only the effort was not taken. The table's log says, with the time, when a host's program starts for its models and how it ended, and each look at an account and what it found (in, out, not known), nothing of what the program printed. It says too how a chat's program let go ended, by itself or stopped.

`rpg launcher` ([server/launcher/](../src/server/launcher/)) serves a page of the campaigns of this computer at `127.0.0.1`, on the first free port from 5750 to 5759, behind the gate it shares with the dashboard ([server/page/](../src/server/page/)), and writes where it is found in the player's data folder (`launcher.json`, with a token new at each start). It lists the campaigns it remembers, those in the folder of new campaigns (`RPG Engine` in the player's home) and those whose table left its place; it makes a new one as `rpg init` does, as the player, and opens one by starting its table apart, then, once that answers, opening the table's page in an application window of its own, one at a time for an address, and answering `{url, window}` (with `root` for a new one): with `window` false, where no Chromium opens one, its own page goes there; a table of another engine is never ended from here. It ends by itself after ten minutes with no page and no request; of two started together, the one whose place stays a second later keeps it, and the other gives its link and ends. A campaign that cannot be read now, as one on a disk that is not there, stays in the list with why; each folder is first asked whether it answers, all together and without blocking, and one that does not within a second, as a network share that is away, is listed as such and not read; whatever fails in a route is logged, the page reads what to do, and the launcher goes on. Every folder the page names is resolved first, so that a folder written another way is the same campaign and finds its table; any whole path is opened, added or forgotten, so that whatever is in the list can be taken off it; on Windows the folder a new campaign is made in is refused where its name ends with a dot or a space, or is a device's, with an extension or not, and a campaign's name never gives such a folder. The page opens the campaign its address names (`?open=`) only when it is in the list. `rpg open`, which the icon on the desktop runs, finds the launcher or starts it apart, asks one of another engine to quit with its token, and opens its page in a browser's app window, else a tab ([desktop/](../src/desktop/)); `rpg open` and `rpg icon` end once their line is written, as nobody reads the icon's console, which is a terminal all the same: there the question whether to put the icon on the desktop is never answered, and waits a minute at most. Each host the page offers says its account, signed in, out or unknown, and how it is signed in and installed ([helpers/access.ts](../src/helpers/access.ts)): Claude Code's and Codex's account is asked of their own status in the background, never while a request waits, kept a minute and looked at again on `{ hosts: true }`; their sign-in starts from the page (`{ signIn: { host } }`, cancelled with `cancel: true`), runs their own login command, which opens the browser, and is followed until it ends; the engine installs them with npm in its own folder (`{ install: { host } }`); one sign-in of a program and one installation at a time on the computer, whatever launcher or table asks, by a mark in that folder that a process gone never holds: another window's under way is said with `signInCode` or `installCode` `elsewhere`, and forgotten once a look finds the account changed; Antigravity and OpenCode sign in and install from their own app and page. A status too slow, failed or unreadable is never signed out: the account stays as last known. Each change reaches the pages as a notice. The folder window the page asks for (`{ pick: { title?, start? } }`, or `{ pick: true }`) is the system's own, one at a time, titled with the words of the control clicked and opened in the folder of new campaigns ([confirm/](../src/confirm/)): on Windows Explorer's, from a hidden PowerShell, owned by an invisible window on top of the others so that it opens over the browser; osascript, zenity or kdialog elsewhere. The sizes of the windows are kept in [desktop/window/](../src/desktop/window/): the launcher's 960 by 680, a campaign's nine tenths of its screen's free room, at most 1920 by 1200, both centred. On Windows the process that opens a window places it from outside: PowerShell, given its script on its input, starts the browser, waits for its new window with a title of ours (the address while the page loads, then the page's title) and places it by that window's DPI in the work area of its monitor, one script at a time on the computer, never another window, as a page cannot (Brave shows it a made-up screen, a browser already running takes no size from its command line); elsewhere the address is marked `opened` and the page sizes its own window. Only an address `http://127.0.0.1:<port>` is given to a browser, and a place with another link is no place. Whoever looks for the launcher asks `/api/ping`, which reads no disk and answers 503 while the launcher is starting, until it kept its place: who gets it waits and asks again; only a process gone or an address where nothing listens takes its place away; one that is slow or answers wrong is there, and is never doubled: `rpg open` says its process and how to end it. A campaign's page asks for the way back at `/api/home`, which gives the campaign's folder and the launcher's link where one answers; at a table, a POST starts the launcher where none answers and opens its page in an application window of its own, answering `{url, window}`. The table and the dashboard never import the launcher: the CLI gives `rpg table` the way to it.

## 4. Tests

`npm test` runs vitest on `test/`; the 5e, Ironsworn and our extensions keep their tests in their own repos, and `npm run test:downstream` runs them against this engine, with the 5e beside the others whose tests play it. Commands are tested through `runCommandLine(args, testContext(folder))`; `*-laws.test.ts` check rules with fast-check on random worlds. The tests play [test/systems/fake](../test/systems/fake/), a game system of names and shapes of its own made for them, never published, and `free`; a test that needs a system without something makes one in a temporary folder (`madeSystem` in [test/support.ts](../test/support.ts)). [test/system-packages.test.ts](../test/system-packages.test.ts) checks every installed system with the kit's `systemChecks`, which a system's repository runs on itself.

## 5. How to add things

**A command.** Create `src/commands/<name>.ts`, or the file in its topic's folder, with `defineCommand`. In `run`: `requireCampaign`, `campaignWorld`, read with `effectiveFields`, check everything, write through the modules, log. Return a result; `format` tells the AI what happened and what next. Add it to [commands/index.ts](../src/commands/index.ts), test it through `runCommandLine`, run `npm run docs`.

**A field kind.** Add it to `fieldKinds` in [core/field-kind.ts](../src/core/field-kind.ts), give it a meaning where kinds are read (`declaredKind` in [pages/system-pages.ts](../src/pages/system-pages.ts) and its callers), and its check to `fits` in [testing/system-checks.ts](../src/testing/system-checks.ts).

**A key of `system.yaml`.** Add it to `systemSchema` in [systems/schema.ts](../src/systems/schema.ts) and to `readSystem` in [systems/read.ts](../src/systems/read.ts), use it from a command helper, check it in [testing/system-checks.ts](../src/testing/system-checks.ts) when a value of it can be wrong, have the fake system use it, describe it in [game-systems.md](game-systems.md).

**A page of a system.** Add `world/<type>/<Name>.md` in the system's own repository; the kit's `systemChecks`, in its tests, checks its name, fields and links. Only open-licensed content, with its attribution.
