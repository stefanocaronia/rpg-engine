# rpg-engine — guide for development agents

**rpg-engine** is a toolbox that lets a high-level AI run a tabletop RPG campaign: the AI invents, plays and rules; the tool remembers, rolls the dice and keeps the accounts. A campaign is a folder of markdown files.

This file is about **developing** rpg-engine. The instructions for **playing** are part of the product: see "Development vs game".

## Read first

- `docs/architecture.md`: a short map of the code. `docs/game-systems.md`: what a `system.yaml` can declare, and how a campaign adds what a system lacks. `docs/commands.md`: every command and its parameters, generated by `npm run docs` (a test fails when it is stale). Update them in the same commit when a change alters what they describe, and keep them short: they are public, a map and a reference, never a history; the code says the details. No decision numbers or Italian in them.
- `private/project/GLOSSARIO.md`: the Italian terms of the project docs and their names in the code.
- `private/project/README.md`: index of the project docs (in Italian). `private/project/PLAN.md` says what comes next.
- The project docs hold only what the maintainer has decided, written briefly. Proposals go to `private/project/DECISIONI.md` under "Da decidere" until the maintainer decides. No premature detail (code, examples, formats, diagrams) before the work it belongs to.
- `private/project/IDEE.md`: the maintainer's idea inbox. When it has entries, fold each idea into the right document, delete it from `IDEE.md`, and tell the maintainer what changed.
- `private/` is the maintainer's private repository, ignored by this one: the project docs (`private/project/`) and the colleagues (`private/.claude/`, which `.claude` links to). Commit it with `git -C private` from the root; to search it, give `private/` as the path. Never delete through the link (`rm -rf .claude/`), never `git stash --all`, and `git clean -ffdx` only with `-e private`. After moving or copying the repo, run `node private/link.mjs`. If `private/` is missing (e.g. in a fresh clone), ask the maintainer. `private/project/archivio/` is history.

## Commands

- `npm run build`: compile `src/` into `dist/`.
- `npm test`: run the tests.
- `npm run format`: format the code (ESLint fixes, then dprint).
- `npm run lint`: check the formatting, and the types of the tests too, as CI does.
- `npm run docs`: write `docs/commands.md` from the commands' definitions.
- `npm run demo`: build, then serve the dashboard of the demo campaign at `http://127.0.0.1:5760`, asking checks in turn: what the browser pane's play button starts (`.claude/launch.json`).
- `npm run betasim`: build, then run betasim's flows and simulated testers on the dashboard, at 1280 and at 375 (`test/betasim/`): its usability alone, never the game. Reports in `test/betasim/report/`.
- `npm run translate`: translate the dashboard's phrases that a shipped language lacks (`src/dashboard/i18n/<code>.json`), a game system's words from its Italian list (`systems/<name>/words/<code>.yaml`), and the guide of Help where a language lacks it or has one from an older English (`src/dashboard/guide/<code>.md`), with Claude Code and your own login; `-- --only fr,de` for some. Italian is curated: read what it writes there.
- Releasing: a tag `v<version>` equal to `package.json`'s version publishes it to npm through GitHub Actions (`.github/workflows/publish.yml`), after lint, build and tests; only on Stefano's word.
- `npm link`: install the development build as the global `rpg` command. An MCP server that is already running keeps the code and the game systems it started with: after a build, reconnect it (`/mcp` in Claude Code, `/mcp refresh` in Gemini CLI) or open a new chat.

## Development vs game

1. **No "magic" names for game files in the repo.** Nothing under `instructions/`, `systems/`, `extensions/` or `playtests/` is called `AGENTS.md` or `CLAUDE.md`, and nothing sits in `.agents/` or `.claude/`: hosts load those on their own, and a development agent would take the game master's instructions as its own. The files get their real names only when they are installed into a campaign.
2. **Playtests with an AI run in a campaign outside the repo.** Claude Code also reads the `CLAUDE.md` files of parent folders, so inside the repo development and game instructions would mix.

## Architecture rules

- **Keep it simple.** The core only does what an AI is weak at: memory, dice, bookkeeping, time, maps and positions, secrets, text lookup.
- **Don't encode game rules.** Ruling is the AI's job, with the exact text at hand.
- **A system works out the sheet, not the game.** It computes only the numbers of the character sheet and the resources that are spent and come back, as D&D Beyond does; every other feature, item or interaction stays text the AI reads and applies. A new mechanic comes only when a playtest shows the AI getting that count wrong, never because a review finds an edge case: in a review, an edge case of the rules becomes text for the AI.
- **Core, system or extension?** Core code must make sense for a game very different from D&D. Anything that names a game's concepts (HP, spell slots, advantage) belongs in a system or an extension, as data; their code only when data is not enough.
- **Data is object-oriented and SOLID.** Each page describes only itself. A relation lives in whoever holds it: who contains, owns or knows something keeps the list, with links, in its frontmatter; a thing never records where it is, who has it or who knows it. The engine works out where a thing is by climbing its containers. Systems and extensions add types and fields without changing the core ones.
- Every operation is a command defined once, from which the CLI and the MCP server are generated, and later the dashboard's API. Every command validates its input and, when it changes something, writes a line to the log; the caller's role is checked once roles exist (phase 2).

## Coding guidelines

Clean, compact, ordered code that is easy to understand.

**Design first**
- Think the architecture before writing code: which module owns the change, its public API, its dependencies. For anything non-trivial, propose the design to the maintainer and wait for approval.
- Each module (a folder under `src/`, such as `dice/`) does one job, exposes a small API from its `index.ts` and depends only on core utilities: never on commands, the CLI or other modules. Commands are the glue between modules.
- SOLID: one responsibility per module and function; add behaviour with new modules and commands instead of bending working ones; inject what comes from outside (randomness, time, folders) through `Context`.
- No over-engineering: the simplest code that solves today's need, with no speculative options, layers or abstractions.

**Formatting** (applied by `npm run format` and on save in VS Code with the recommended extensions; checked by `npm run lint` and CI)
- 4-space indentation (2 in JSON and YAML, as npm writes them), lines up to 240 characters, double quotes, semicolons.
- Braces on their own line for classes, interfaces, functions and methods; on the same line for `if`, `else`, loops, `switch`, `try` and arrow functions, with `} else {` on one line.
- Braces always, even around a single statement.
- A blank line before and after every block statement (`if`, loops, `switch`, `try`); never more than one blank line in a row.

**Code**
- Extract a function when a block becomes complex or is needed twice; prefer well-named functions to sections marked by comments.
- Clear, descriptive names; no abbreviations or cryptic names (`context`, not `ctx`), except loop indexes.
- camelCase for variables, functions and constants; PascalCase for types, interfaces and classes, without an `I` prefix; no underscores or hyphens in identifiers. File names in kebab-case.
- Public API first in a file, private helpers below it.
- Let TypeScript infer local types; annotate parameters and return types of exported functions.
- Relative imports use the `.ts` extension; the build rewrites them to `.js`.
- Comments in English, one or two lines at most: the code should explain itself. A one-line `/** */` on exported functions and types when the name is not enough.
- Error messages say what went wrong and how to fix it: an AI reads them.
- Use our core utilities before writing new helpers.
- Test every module through its public API, with randomness and time injected.

## Tools and checks

- **CodeGraph** (`@colbymchenry/codegraph`, optional, set up per person): when `.codegraph/` exists, use it before Grep/Read chains for structure questions (who calls X, what Y reaches, what breaks if Z changes), then confirm in the file. After editing, run `codegraph sync .` before asking it about the changed files. Agents never run `init`, `index` or `uninit` for the maintainer.
- **Jev** (`mcp__jev__*`, optional, set up per person): before a commit, `jev_gate` with the diff, the claims of the commit message and the real test output; before reporting results, `jev_verify` the claims against the evidence. Fix or drop unsupported claims. Without Jev, say so and go on.
- **betasim** (devDependency from the private repository `stefanocaronia/betasim`, shared with TimerLines): flows in YAML that must pass, and testers made of numbers that measure the path on the real page (targets, hidden commands, jargon, names for a screen reader); its LLM testers only when Stefano asks, as they cost. Improvements to betasim go to its repository.
- **Looking at the dashboard**: a change to the page is judged on the page, not in the code. `test/demo/look.ts` opens it in Chrome with Playwright (the Chrome installed) on the demo campaign of `tmp/dashboard-demo`: a screenshot, what the console said and the accessibility tree, at the width and in the theme asked; `test/demo/dashboard.ts` serves the same campaign for the browser pane, as `npm run demo` does. Both need `npm run build` first, which `npm run demo` runs.
- **Core mechanics** (inheritance, then counters, time, scenes, containers, links and secrets) follow numbered rules in `private/project/MECCANICHE.md`. Their tests cite the rule codes: a table of cases, property tests with fast-check on worlds generated at random, and once per mechanic a mutation-testing run. A change to a mechanic changes its rule first, with the maintainer.
- **Regression check after every addition or change**: build and run all tests; check the callers and impact of every changed symbol with CodeGraph; review the diff for regressions, unhandled `undefined`, nondeterminism, simplicity and these guidelines, and fix what you find; bring the docs in `docs/` up to date with the change (`npm run docs` for the commands). When it matters, give the maintainer a short checklist to verify the behaviour.

## Conventions

- TypeScript on Node ≥ 22; zod; yaml; the official MCP SDK; Preact with JSX for the dashboard; vitest; few dependencies.
- Code, comments, commit messages, public docs, command names, file names and config keys in English; game content in the campaign language.
- Secret parts of a page go in a `> [!secret]` block (Obsidian callout).
- Tests use Ironsworn next to `5e`, to keep the core generic: only its CC BY 4.0 parts (the SRD, asset cards and oracles; from Delve, moves, oracles, theme and domain cards), with its attribution.
- Never keep the repo under a path containing `&`: on Windows, npm's `.cmd` shims truncate the path and `npm run` fails.
- Credentials never go in the repo or in a campaign: they belong in the OS keychain.
- **Licensing and trademarks.** The repo and the npm package hold only original or open-licensed content: for 5e, only SRD 5.1 and 5.2 (CC-BY-4.0) with the required attribution, and compatibility stated only as "compatible with fifth edition". No Wizards of the Coast trademarks in names or presentation, no non-SRD content (Forgotten Realms, non-SRD monsters, art), not even in tests. These rules cover only what we ship: never restrict what a user's AI knows, searches or reads.
